# Хаос-тесты

Сценарии раздела 18.3 [Botsight.md](../Botsight.md) против стека docker compose. Каждый сценарий:

1. запускает `loadgen` как парк SDK: тот же `batch_id` на каждом повторе, повторы до 3 минут, 2 % батчей отправляются дважды намеренно;
2. под нагрузкой ломает одну часть стека и чинит её;
3. сверяет ClickHouse с журналом принятых событий.

Критерий прохождения: строк в ClickHouse = уникальных `event_id` = уникальных строк журнала, ни одного брошенного батча, и в самом журнале нет повторов (иначе ошибка генератора спряталась бы за сравнением).

```bash
docker compose -f deploy/docker-compose.yml --profile chaos up -d --build api collector chwriter toxiproxy
loadtest/chaos.sh                      # все сценарии, ~6 минут
loadtest/chaos.sh kafka_stop network   # выборочно
```

`RATE` (событий в секунду, по умолчанию 3000) и `DURATION` (по умолчанию 45s) меняют нагрузку. Отчёт пишется в `/tmp/botsight-chaos/report.md`. В CI это workflow `chaos`: вручную, каждую ночь и на PR, меняющих сценарии, генератор или стек.

## Сценарии

| Сценарий | Сбой | Что должно произойти |
|---|---|---|
| `collector_kill` | `kill -9` collector на 5 с | генератор повторяет батчи, потерь и дублей нет |
| `chwriter_kill` | `kill -9` ch-writer посреди пачек | после рестарта пачки собираются с теми же границами и токенами, ClickHouse отбрасывает повторную вставку |
| `clickhouse_pause` | `docker pause` ClickHouse на 30 с | растёт лаг Kafka, после паузы ch-writer догоняет |
| `kafka_stop` | Kafka остановлена на 20 с | collector отвечает 503, генератор повторяет, батч в Kafka целиком или никак |
| `network` | toxiproxy: +300 мс, 10 % ответов оборваны | ответ потерян после приёма — повтор получает «duplicate» и считается принятым один раз |

В сценарии `network` генератор открывает соединение на каждый запрос (`-keepalive=false`): toxiproxy применяет `toxicity` к соединениям, а не к запросам, и при keep-alive пять процентов могли не задеть ни одного из восьми соединений.

## Результаты

Ноутбук Apple M5, всё в docker compose на одной машине, 3000 событий/с, 45 секунд нагрузки на сценарий.

**До исправления.** Один сценарий провален:

| Сценарий | В журнале | Строк в ClickHouse | Дублей | Ответы collector | Итог |
|---|---|---|---|---|---|
| collector_kill | 113 600 | 113 600 | 0 | 202:1162 | PASS |
| chwriter_kill | 135 200 | 135 200 | 0 | 202:1386 | PASS |
| clickhouse_pause (лаг 82 тыс.) | 135 200 | 135 200 | 0 | 202:1376 | PASS |
| **kafka_stop** | 53 100 | 53 319 | **219** | 202:540, 503:5 | **FAIL** |
| network (87 потерянных ответов) | 103 100 | 103 100 | 0 | 202:1056 | PASS |

У всех 219 задвоенных событий по два разных `received_at`, то есть каждое пришло в двух HTTP-запросах. Брокер останавливался посреди записи батча: часть записей была подтверждена, collector отвечал 503, а повтор SDK записывал эту часть второй раз. Исправление — #32: батч пишется транзакцией Kafka с групповой фиксацией, потребители читают `read_committed`.

**После исправления** все сценарии проходят:

|---|---|---|---|---|---|
| collector_kill | 113 600 | 113 600 | 0 | 202:1153 | PASS |
| chwriter_kill | 135 200 | 135 200 | 0 | 202:1383 | PASS |
| clickhouse_pause (лаг 90 тыс.) | 135 200 | 135 200 | 0 | 202:1386 | PASS |

## Что ещё нашлось по дороге

Две ошибки нашлись в самом генераторе нагрузки, а не в Botsight. Обе сделали бы результат недостоверным:

- **Дубль на повторе считался отказом.** Генератор принимал ответ «duplicate» на повторной попытке за отказ, хотя на деле батч был принят, а терялся только ответ на первую попытку. Такие события есть в ClickHouse, но не в журнале. Теперь «duplicate» на повторе означает «принято раньше».
- **Намеренный повтор попадал в журнал дважды.** Если первая попытка намеренного повтора обрывалась, вторая получала «duplicate» и после первого исправления засчитывалась как принятая. Её события попадали в журнал второй раз. Теперь намеренный повтор журнал не трогает, а сверка проверяет, что в журнале нет повторов.

Кроме того, прогон упёрся в защиту регистрации: 10 аккаунтов в час с одного адреса. Скрипт регистрировал аккаунт на каждый сценарий. Теперь аккаунт один на прогон, а проекты создаются через API.
